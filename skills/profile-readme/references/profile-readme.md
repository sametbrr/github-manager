# Profile README standard

The profile README is `README.md` in the `<login>/<login>` repo. GitHub shows it on top of the
profile page. Section order comes from `profile.sections` in the config
(`../../gh-audit/references/config.md`); the default is `intro, about, projects, contact`.

## Section catalogue

Use only the sections listed in `profile.sections`, in that order. Omit a section when there is no
real data for it; never leave a placeholder.

| Id | Heading (EN) | Content | Data source |
|---|---|---|---|
| `intro` | none (top block) | `# <name>`, one tagline line, optional one-line mission, optional badge row (site, social, package registries) | `gh api user`, social accounts |
| `about` | About | 2–5 sentences or a short list: what you work on, with what | ask the user; current bio |
| `projects` | Projects | table or list of public repos: name link + canonical description | `gh repo list` (non-fork, non-archived, public), pinned repos, `profile.projectSources` |
| `packages` | Packages | published packages with registry badges (npm, NuGet, PyPI, crates, Go) | repo homepage URLs, manifests |
| `focus` | Current Focus | 2–4 themes, bold title + one sentence | ask the user |
| `writing` | Writing | latest posts or talks | blog RSS or a list from the user |
| `stats` | GitHub Stats | third-party stats cards (only if `profile.stats` is true) | none |
| `contact` | Contact | links: site, email if public, social accounts | `gh api user`, social accounts |
| `custom:<Title>` | `<Title>` | any section the user defines | the user |

## Rules

1. Primary file in `language` (default English). Each code in `profile.mirrors` gets a full
   translation `README.<lang>.md` with the same sections, same badges and untranslated code.
   Link the mirrors from the primary file right after the intro block.
2. Project lists use the canonical repo descriptions (after `gh-normalize`), not invented text.
3. Keep hand-written sections the user added, unless they ask to drop them.
4. Badges: one consistent style per row; only for accounts and packages that exist.
5. No hidden tracking pixels or third-party widgets unless the user opts in (`profile.stats`).
6. No agent or tool attribution footer ("generated by …") unless the user asks for one.
7. Pushing is outward facing: show the diff and wait for explicit approval before commit or push.

## Generated profile READMEs

Many profile READMEs are built by a script or a GitHub Action from a data source. Editing the
output by hand breaks the next build or fails a CI check. Treat the README as generated if any of
these is true:

- a comment marker in the first lines: `Generated`, `auto-generated`, `DO NOT EDIT`,
  `<!-- START_SECTION`, `<!-- BLOG-POST-LIST:START -->`, `readme-tools`, `<!-- generated by`
- `package.json` has a script whose name or command mentions `readme` (`readme`, `readme:check`,
  `build:readme`, `generate`)
- a workflow in `.github/workflows/` writes or checks `README.md` (`readme`, `blog-post-workflow`,
  `github-readme-stats`, `waka-readme`, `git commit` of README, a `--check` diff step)
- a template file exists: `README.tmpl`, `README.md.tpl`, `templates/README*`, `scripts/*readme*`
- data files that obviously feed it: `content/*.yaml|json|md`, `data/profile.*`

If it is generated: find the source and the generator command, edit the source, run the generator,
run its check command if one exists, and show the resulting README diff. If you can't tell which
file is the source or the generator fails, stop and ask the user. Never hand-edit the output.

## Checklist

- [ ] Sections match `profile.sections` order; no empty sections
- [ ] Name and tagline in the intro
- [ ] Projects use canonical descriptions; no archived or forked repos unless chosen
- [ ] Mirrors exist for every `profile.mirrors` code and are up to date
- [ ] Generated README: source edited, generator and check run
- [ ] No unrequested attribution footer
